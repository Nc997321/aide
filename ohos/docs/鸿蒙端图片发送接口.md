```
    → relay（哑管道，透传）
    → Rust REGISTRY send_message
      handlers.rs:36 SendMessageArgs { images: Option<Vec<Value>>, display: Option<Value> } ✅ 已就位
    → commands/chat.rs attach_images（原样透传，不校验结构）        ✅ 已就位

      { data, mediaType } → Anthropic content block {type:"image", source:{type:"base64",...}} ✅ 已就位
    → pushUserMessage 广播 user_message { text, display } → 桌面/PWA 渲染
```

鸿蒙端要改的只有两处：

| 位置 | 现状 | 改成 |
|---|---|---|
| `ohos/entry/src/main/ets/sdk/api.ets:73` | `images: null;`（占位） | `images: ImageAttachment[] \| null` |

## 二、契约 1：images 字段

**形状**（与桌面 `ImageAttachment` 同形，`packages/aide-sdk/src/composables/useChatSession.ts:54`）：

```jsonc
"images": [
  { "data": "<裸 base64，无 data: 前缀>", "mediaType": "image/jpeg" }
]
```

**铁律（违反即静默炸）**：

1. **键名必须是 `mediaType`，不是 `mime`**。sidecar 消费方 `agent-sidecar/src/mapper.ts:39`
   读的是 `img.mediaType`。⚠️ 注意 Rust 单元测试 `commands/chat.rs:715` 里构造的是
   `{"mime": ...}`——那是测试自身的形状、只验证 Rust 层透传，**照抄必踩坑**：
   键名不对 → `media_type` 变 undefined → 模型 API 在当轮直接报错。
2. **`data` 是裸 base64 字符串**，不带 `data:image/...;base64,` 前缀（SDK 会自己组
   Anthropic 的 source 结构）。
3. **`mediaType` 只允许四个值**（Anthropic API 边界契约，mapper.ts:36 注释同款约束）：
   `image/png` / `image/jpeg` / `image/gif` / `image/webp`。
4. **空文字 + 纯图片允许**：`prompt` 为空串时 mapper 只发 image 块（`mapper.ts:43` 的
   `if (prompt)` 分支），无需造占位文字。
5. 数量建议 ≤5 张/条（PWA 端用同一上限，防 relay JSON 载荷爆炸）。

## 三、契约 2：display 渲染描述（图片消息必带）

**为什么必须带**：三端都不本地渲染用户气泡，只认 sidecar 广播的 `user_message`。
广播的 `text` 取 `display` 里的 text 块，**display 缺失时回落 `prompt`**。所以：

- 带文字的图片消息、不发 display → 其他端显示文字 ✓，但**图片看不见**；
- **纯图片消息、不发 display → `text = prompt = ""` → 桌面/PWA 出一个空气泡**。

所以鸿蒙发图片时**必须构造 display**（块形状 = `packages/aide-sdk/src/types/chat.ts:277`
的 `UserMessageBlock`，sidecar 侧镜像在 `agent-sidecar/src/types.ts:79`，**顺序照抄桌面
`buildUserDisplay`：image 块在前，text 块在后**）：

```jsonc
"display": [
  { "type": "image", "data": "<裸 base64>", "mediaType": "image/jpeg" },
  { "type": "text", "text": "用户打的那段话（没有文字就不放 text 块）" }
]
```

Rust 层 `handlers.rs:43` 已收 `display: Option<Value>` 原样透传——鸿蒙 DTO 里没有
display 字段不影响（serde 可选），加上即可。

**接收侧（鸿蒙 v1 渲染别人的消息）**：`user_message` 事件的 `display` 里会出现
`{type:"image"}` 块。不识别就降级成纯文本气泡（`text` 字段兜底），**整条消息不能
消失**——这是既有约定，不渲染图片也不报错。

## 四、压缩与体积

| 项 | 建议值 | 理由 |
|---|---|---|
| 长边 | ≤1568px | Anthropic 视觉有效分辨率，再大只烧 token 不涨识别 |
| 重编码 | JPEG quality 0.85（原 PNG ≤1.5MB 且 ≤1568px 可原样直传） | 手机照片 3-8MB 原样传不动 |
| 单图 base64 | ≤5MB（API 硬限），建议压完 <500KB | relay WS JSON 单条载荷余量 |

PWA 参考实现（同策略）：`remote-pwa/src/imageEncode.ts`——小图直传保 PNG 锐度、
大图缩放转 JPEG、压完仍超限抛错。

## 五、ArkTS 实现要点

1. **选图**：`photoAccessHelper.PhotoViewPicker`（系统相册选择器），支持多选时自己截到 5 张。
2. **缩图**：`image.createImageSource(fd)` → `createPixelMap`（带 desiredSize 降采样）→
   `image.ImagePacker.packToData`（`format: "image/jpeg", quality: 85`）。
   鸿蒙 API 的 desiredSize 是**整数倍降采样**（非任意缩放），需要任意目标尺寸时
   降采样后再用 PixelMap 的 scale 或分两步逼近——保底策略：只要长边 ≤1568 就不再缩。
3. **base64**：`util.Base64Helper` 的 `encodeToStringSync(Uint8Array)`。
4. **入参组装**：把 `SendMessageParams.images` 从 `null` 换成附件数组；有图时同时带上
   `display`（§三）。

## 六、自验方法

1. `pnpm tauri dev` 起桌面 + relay，鸿蒙连上后发一条带图消息：
   - 桌面端用户气泡应显示图片（不是空气泡/纯文本）；
   - 模型回复应体现"它看到了图"。
2. 反向验证接收侧：桌面端在共享会话里粘贴一张图，鸿蒙端至少显示纯文本（不消失）。
3. 键名对不对的最快判据：发一条图后看模型回复——**当轮报 400/invalid image** 基本
   就是 `mime`/前缀/媒体类型三处之一错了。
