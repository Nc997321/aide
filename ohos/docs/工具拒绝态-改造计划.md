# ohos 端「工具拒绝态」改造计划

> 配套：桌面端显示形态原型 `docs/superpowers/design-previews/2026-09-08-tool-denial-state.html`
> （四个候选形态 + 基线）。桌面端定稿后 ohos 照搬同一形态，不要各做各的。

---

## 一、为什么要改（缘由）

**事故起点**：用户在权限弹窗点「拒绝」并填写理由后，理由被裸塞进被拒工具的
`tool_result` 正文。模型在读「我刚跑的这条命令的输出」的位置上看到一句人话，
于是把它当成工具输出——Write 明明没执行，模型却报告「已创建 test.md」。

**已修的两处（2026-09-08，桌面端 sidecar）**：

1. `agent-sidecar/src/session-worker.ts:634`——策略 ask 时 hook 不再自己弹窗，
   返回 `permissionDecision:"ask"`，把人工确认交还 CLI 的第一类通道（canUseTool）。
2. `agent-sidecar/src/permissions.ts`——新增 `userDenyMessage()` / `policyDenyMessage()`，
   deny 文案套上官方外框（**SDK 通道不做任何包装，外框是宿主自己的责任**——
   `claude.exe` 里带模板的 `cancelAndAbort` 只在终端交互 UI 生效）。
   已实测：转录里 content = 官方外框 + 用户原话，模型正确理解并按附言改写入。

**剩下的缺口是显示层**：这三端（桌面 / remote-pwa / ohos）都只按 `is_error`
画一个红点，正文直接显示外框全文。用户回看历史时：

- 分不清「工具真的报错」和「我自己拒绝的」；
- 自己当时填的附言埋在一大段英文外框里，读不到。

**改的目标**：把「这是一次拒绝」和「用户当时说了什么」两件事在 UI 上分开呈现，
且仍然挂在被拒的那次调用上（不能做成独立的用户消息气泡——见第四节）。

## 二、协议改动（桌面端定稿后 ohos 跟随）

`tool_result` 事件目前只有三个字段（`agent-sidecar/src/types.ts:105`）：

```ts
| { type: "tool_result"; id: string; content: string; is_error: boolean }
```

方案：新增一个布尔 `denied`，**不新增附言字段**（理由见下）。

```ts
| { type: "tool_result"; id: string; content: string; is_error: boolean; denied?: boolean }
```

历史回看链路同步：Rust `src-tauri/src/commands/session/transcript.rs:56-69`
目前只取 `content` + `is_error`，`toolDenialKind` 在该行顶层但没读；要补读并填
`denied`，否则会出现「刚发生的能看、回看没有」——比现状更困惑。

**为什么不带附言字段、而是从 content 剥前缀**：

- 历史路径读的是 jsonl，那里只有 `content`，没有独立的附言字段；
- 若实时路径单独带 `deniedFeedback`，实时与历史就是两套真相，必然漂移；
- 所以统一由「剥离官方外框前缀」派生，前缀常量放 `packages/aide-sdk`
  共享（sidecar 拼装、三端剥离同一个常量），避免两处漂移。

> **未定事项（要实测）**：`toolDenialKind` 是否出现在 SDK 流对象里——它没在
> `sdk.d.ts` 声明，目前证据来自 CLI 写盘的 jsonl。若流里读不到，`denied` 退化为
> 「`is_error` + content 命中我们自己的外框前缀」判定。判定逻辑同样放在共享常量里，
> ohos 直接调用，不要自己写一份字符串匹配。

### ohos 与桌面端的结构差异（这点要单独决策，别照抄）

桌面端有完整的「工具卡」实体（`src/components/ToolCallBlock.vue`），而 ohos V1：

- **实时路径没有已完成工具卡**——工具调用只以 `LiveActivity` 存在于时间线
  （`ChatPage.ets:753` `liveRow`），`tool_result` 一到就 `removeLiveActivity`
  （`ChatEvents.ets:104`），卡片随即消失；
- **历史路径才有工具块**——`ChatTranscript.ets:65` 由 `tool_call` block 构造。

所以 ohos 有两条路，需要你选：

- **I. 最小改**：只补历史路径的拒绝态渲染。实时路径照旧（拒完就消失），
  用户回看时才看得到。改动最小，但和桌面端实时可见不一致。
- **II. 对齐桌面端**：`tool_result` 到达时若 `denied` 为真，不直接删
  `LiveActivity`，而是转成一条带 `denied` 的 `ToolCallBlock` 留在时间线。
  一致性最好，但要动实时渲染链路，工作量明显更大。

我的建议是先做 I（历史可见已经解决「回看分不清」这个主诉），II 等桌面端定稿、
且 ohos 有了通用工具卡组件后再补——否则会在 ohos 里为拒绝态单独造一个只有它用的
卡片组件，属于提前特化。

## 四、不做成「用户消息气泡」的三条硬理由

1. **回看读的是 jsonl**：拒绝记录在转录里是 `tool_result` block，不是一轮 user。
   要显示成气泡，就得在解析时凭 `denied` 伪造一条 user message——违反「用户气泡
   单一渲染来源 / UI 只认事件通道」这条红线，且实时与回看两套真相。
2. **丢绑定**：「别删这个目录」脱离被拒的那次调用就没有意义。
3. **真要做成气泡也有干净办法**——真发一轮用户消息（`pushUserMessage`），转录里
   就是真实 user turn。但那样理由会投递两次（一次在 tool_result 外框给模型，
   一次作为用户轮次），多一轮 token，且顺序上理由出现在拒绝之后。当前模型已经
   正确理解，不值得付这个代价。

---

## 五、验收点

1. 拒绝一次并填理由 → 工具卡显示「已拒绝」态（与真报错的红点明显不同）；
2. 同一条记录，附言单独可读，不埋在外框英文里；
3. **重开会话回看同一条记录，形态与实时一致**（这条最容易漏，历史路径单独走 Rust 解析）；
4. 真报错的工具卡仍然是红点 + 错误态，不被误伤；
5. 与桌面端同一形态（对照 HTML 原型）。
