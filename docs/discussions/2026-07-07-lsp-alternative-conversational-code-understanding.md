# 讨论记录：LSP 替代方案 — 对话式代码理解

日期：2026-07-07
状态：方向已拍板，**尚未进入正式 brainstorm/spec/plan 流程**，先记录讨论过程供后续立项时铺垫。

## 起点：想给 Aide 加 LSP，但不想变重

最初的诉求是"想让 Aide 有 LSP 的能力，但不希望引入真正的 LSP 导致产品变重"（常驻语言服务器进程，rust-analyzer/tsserver/jdtls 这类在大项目下随便涨到几百 MB~1GB+ 内存）。

讨论先拆成了两个完全不同的场景，因为它们对应的架构天差地别：

1. **Agent 自己写代码时不写错** —— 靠自动化的编译/测试反馈闭环，不需要 LSP。
   - 关键发现：`@anthropic-ai/claude-agent-sdk` 自带 hooks 机制（`PostToolUse`/`PostToolBatch` 等），支持注册 JS 回调、拿到结构化的 `tool_name`/`tool_input`/`tool_response`，并能通过 `additionalContext` 把结果塞回模型下一轮上下文（见 `agent-sidecar/node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts`）。
   - 思路：`PostToolBatch` 触发一次真实工具链检查（`cargo check` / `vue-tsc --noEmit` / `eslint`），把结构化错误通过 `additionalContext` 喂回去，让 Agent 在用户看到结果前就自己发现并修掉问题——压缩"人工发现 → 贴日志 → Agent 改"的反馈循环。不需要常驻进程，跑完即退，比 LSP 更准（编译器是 ground truth，LSP 常为实时性做增量近似）。
   - **此方向本次只讨论到方向层面，未细化触发粒度/UI 呈现/项目类型探测等设计问题，留待后续单独讨论。**

2. **人想了解一块业务代码是怎么回事** —— 本次讨论的主线，见下文。

## 主线：对话式代码理解

### 为什么不是 LSP

真实需求不是"点一下看这个符号的类型和定义在哪行"（LSP 的强项，原子级、点对点），而是"一整条业务链路是怎么走的"（图遍历 + 归纳总结）。LSP 完全不懂"业务"是什么，只懂语法和类型，解决不了这个问题。

### 另辟蹊径的方向

不做 LSP，做**内建的轻量代码知识图谱 + 对话式/可视化探索**：

- 用户自己的权限记录里已经有 `mcp__codebase-memory-mcp__search_graph` 等工具在用——说明"图谱化理解代码"这个心智模型已经被验证有效，只是目前只服务于用户本人在 Claude Code 里的用法，不在 Aide 产品内。
- 设想两条腿（本次只讨论到方向，未展开设计）：
  1. **对话式**：在 Aide 聊天里问"这个业务流程怎么走"，Agent 用图谱/追踪类工具作答，答案可能带一个新的消息块类型做可视化（调用链/流程图），而不是纯文字。
  2. **面板式**：FileViewer 加"关系"侧栏，点符号看定义/调用者/被调用者，数据来自离线构建、增量更新的静态索引（tree-sitter 语法级解析，不做类型系统级语义分析）。
- 用户选定优先聊**对话式**这条腿。

### 产品经理视角的可行性讨论

先问了一个扎心问题：**Agent 现场 Grep + Read + 推理，本来就能讲出业务流程（这正是 `business-process-flow-mapper` 技能干的事，零基础设施）——这个功能到底新在哪？**

拆出三种可能的不满，对应完全不同的投入量级：

- **呈现方式差**（文字堆砌看着累）→ 呈现层的活，成本低，路径可点击跳转这类能力甚至已经有了。
- **慢**（大项目现场翻代码耗时）→ 值得考虑预建索引，把"每次现场探索"换成"一次建好、重复复用"。
- **不准**（漏看关键分支）→ 同样指向预建索引/图谱，但引入了新风险：**图谱如果错了，比没有图谱更危险**——用户会基于"看起来权威、实际错误"的结论做判断，这与"大型可靠项目"的定位背道而驰，图谱的准确性兜底策略必须在设计阶段就想清楚，不能留到后面补。

最初建议的分期验证路径（Phase 0 零成本验证痛点 → Phase 1 呈现层小改 → Phase 2 图谱基础设施重投入）建立在"这只是自用痛点"的假设上。

### 关键转折：这也是核心卖点

用户明确了这个需求**既是自己作为开发者的痛点，也是 Aide 未来要给别人用的核心卖点**。这推翻了"将就能忍"的 Phase 0/1 方案作为终点的可能性，因为：

- "Agent 现场 Grep 讲给你听"这件事**没有护城河**——Cursor/Windsurf/裸 Claude Code 都能做到同等水平，靠的是模型能力的"平权"，不是 Aide 独有的东西。
- 要撑起"核心卖点"，差异化只能押注在：
  1. **准确性和速度**——靠预建索引/图谱，秒回答且不漏关键分支（对应 Phase 2 量级的工程投入）；
  2. **呈现体验**——可点的调用链图/流程图，一眼看懂，不是"别人吐文字你也吐文字"。
- 因为要对外当卖点讲，"大型可靠项目"的定位把准确性容错率压得很低——图谱出错时的兜底策略，从"nice to have"变成**上线前必须回答的问题**。

### 结论：并行双轨，而非纯顺序验证

- **轨道 A（自用，随时可跑）**：继续用现有 Agent 能力去用、去感受哪里疼，产出不是"决定做不做"，而是**积累具体失败案例**（漏看了哪个分支、等了多久），这些案例后续会变成轨道 B 的验收标准和测试用例。
- **轨道 B（卖点，需要认真立项）**：作为独立中型项目排期，下场前先想清楚三件事：
  1. 差异化押注在"准确性"还是"呈现"还是两者都要；
  2. 图谱出错的兜底策略；
  3. 这跟现有 FileViewer / GitPanel / ChangeLogPanel 这套"理解 + 编辑 + 追溯"的产品叙事怎么串起来，是锦上添花的孤立面板，还是重新定义 Aide 产品形态的动作。

用户最终拍板：**当独立中型项目排期**。

## 续聊（同日追加）：实体关系图谱 + 落点到具体代码

用户用真实场景把方向具体化：农业项目里"批次"关联多个"设施"，"设施"关联多个"设备"，从"批次"查"设备"要经过这条关联路径。设想是做一个类似 Obsidian 力导向图的可视化关系网（用户配了一张 3D 图谱截图作参考，明确表示**只是想表达"沿关系找路径"的感觉，3D 本身不是硬要求**，2D 力导向图完全可以，甚至可能比 3D 更适合"精确找路径"这种任务，3D 的旋转/遮挡对这个场景是减分项）。

### 为什么"实体关系图谱"比泛泛的"业务流程图谱"更靠谱

之前主线担心的"业务流程追踪不准"，根源是函数调用关系在动态语言/反射场景下是隐式、运行时才能确定的。但**实体关系**（批次/设施/设备的关联）通常是**显式声明**的（ORM 外键字段、`@ManyToOne`/`@OneToMany` 注解、MyBatis `resultMap` 关联、DB 外键约束）——这是静态分析能高置信度提取的结构，准确性风险比追函数调用链低得多。

### 结构层 + 语义层的两层混合架构（用户提议 LLM + 向量索引，讨论后细化）

- **结构层（硬事实，静态分析拿）**：实体关系、显式方法调用链——构成图谱骨架，高置信度，几乎不会错。
- **语义层（LLM + 向量索引，补软事实）**：不是让 LLM 凭空猜代码位置，而是做**语义检索排序**——把业务语言 embedding 后去匹配代码片段（方法名/注释/SQL）embedding，给出候选列表，且候选必须标注来源（"结构引用"vs"语义相似"），用户自己判断可信度。
- 两层信号**不能混在一起模糊可信度**：结构层确定的直接给高置信度入口；结构层找不到的（拼 SQL、反射、动态查询等），才亮出语义层的猜测，标注"待核实"。

### 用真实改代码流程校准"落点"该炸开到哪一层

用户描述了自己改一个具体需求（"从批次查设备时过滤掉已停用的设施"）时的真实操作路径：定位批次业务 → 打开 Controller → 定位到具体接口（`get...`）→ 定位到 Service → 到这一步要决策"在 Service 里新增 SQL 查询用 Java 过滤，还是直接改 Mapper 里的 SQL 过滤"。

这揭示了两个关键设计原则：

1. **Java Spring + MyBatis 这类三层架构（Controller→Service→Mapper）的调用链，本身也是显式方法调用**，跟实体关系一样能被静态 AST 分析几乎完整还原，不需要 LLM 参与骨架构建——这条项目的地基比最初设想的更稳。
2. **图谱不该替用户做"改 Java 还是改 SQL"这类技术决策**，而应该把两个候选修改点的**真实代码内容**（Service 方法现状 + Mapper SQL 现状）并排展示，5 秒钟带用户到场，决策权留给人。

同时指出静态调用链会漏掉的部分，必须靠语义层"提示、非确定"式兜底：Spring AOP 切面（权限校验/日志/缓存可能悄悄插一刀）、事件/异步/MQ（下游监听者跟当前调用链断开）、定时任务（不经过 Controller 触发）。

### 战略收窄：目标场景明确为"业务/中台/CRUD 形状的软件"，不追求操作系统内核级代码通用性

用户追问"如果用户面对的是操作系统级别代码呢"，讨论后达成一致：**技术套路（结构层打底 + 语义层补漏）本身通用，但结构层能覆盖的复杂度比例在两类代码上天差地别**：

- 业务 CRUD 代码：真正的复杂度几乎全在"数据怎么流转"，恰好是最容易结构化提取的部分，结构层能吃下大头，图谱"看起来完整"站得住。
- 操作系统级代码：真正的复杂度在于任何静态图谱都画不出来的隐性知识（中断上下文、锁语义、内存序、`#ifdef` 编译期分支、`file_operations`/`inode_operations` 这类 ops 表间接分发——间接分发在内核代码里是常态而非例外）。图谱在这里越"看起来像全貌"，越危险，因为真正致命的坑一个字都没画出来。

结论：**主动收窄目标场景到业务/中台/CRUD 形状的软件，不追求内核级代码的通用性**。理由不是做不到，而是——系统程序员领域已经有专用工具（cscope/LXR/ftrace/内核文档）把关键痛点解决得更好，追求"什么代码都能用"的通用性会指数级放大工程风险，换来的却是一个早有更好工具、打不过的战场；而用户自己的真实痛点例子（批次/设施/设备）恰恰就是结构层友好的业务软件，现实世界里"大型可靠项目"的大多数也是这种形状，收窄不代表阉割卖点，卖点不需要"什么都能干"，只需要"在瞄准的这类项目上，别人做不到我们能做到"。**用户认可此收窄立场。**
