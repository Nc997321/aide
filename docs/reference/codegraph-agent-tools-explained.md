# CodeGraph Agent 工具：从零理解这套系统

> 写给完全不了解这个领域的读者。读完你应该能讲清楚：代码索引是什么、嵌入是什么、MCP 工具是什么、为什么模型会"无视"工具、以及我们用了哪三层机制让它不得不用。
> 文中所有例子都来自 aide 仓库的真实实现与 2026-07-25/26 两天的真实调试记录。

## 1. 这套系统解决什么问题

AI 编码助手（agent）每接到一个任务，第一件事是**搞清楚代码在哪**。没有工具时它只有一条路：

```
Grep("canUseTool") → 返回 28 个文本匹配 → 拿不准哪个是定义
→ Read 候选文件（几百行）→ 再 Grep 缩小范围 → 再 Read …
```

每一次 Grep/Read 都是一次工具调用，读进来的原文还要进上下文（之后每一轮都要为它付费）。一个"理清权限弹窗链路"的任务，实测要花 19 次 Grep + 12 次 Read。

**如果有一个提前建好的"代码地图"**，agent 就可以直接问："`PermissionManager` 定义在哪？"一次调用拿到精确答案。这就是 CodeGraph agent 工具：把 aide 已经建好的代码索引，暴露成 agent 可以直接调用的三个工具。

## 2. 代码索引：地图是怎么画出来的

### 2.1 tree-sitter：真的能"读懂"代码的解析器

普通的文本搜索（grep）不认识代码结构——它不知道 `save` 是一个方法名还是注释里的一个词。**tree-sitter** 是一个解析器生成器，能把源码解析成语法树（AST），精确告诉你：这个标识符是类、方法、字段，还是一次函数调用。

aide 的索引构建（`src-tauri/src/codegraph/`）对整个项目跑一遍 tree-sitter，提取两类信息：

| 数据 | 内容 | 存哪 |
|---|---|---|
| **符号定义** | 名字、类型（类/方法/函数/接口）、文件、行号 | `SymbolTable`（内存哈希表：名字 → 定义列表） |
| **调用边** | "函数 A 在第 X 行调用了 B" | `EdgeTable`（双索引：按调用方查、按被调方查） |

一个关键点：这是**名字级**的关联，不是类型级的。两个类都有 `save` 方法时，索引知道"有 2 个 save 定义、5 处 save 调用"，但不知道具体哪次调用对应哪个类——所以它诚实标注 `candidates: 2`，让 agent 自己去读代码消歧。tree-sitter 不做类型推断，这是所有同类工具（包括外部 CodeGraph）的共同上限。

全局命令面板同样保留这些合法的同名定义：它只会按完整的源位置身份（文件、行列、类型、父符号、名称）折叠真正重复的结果，不会按文件或名称合并。列表把文件名和行号前置，并在主题化提示中保留完整相对路径，方便在窄面板中区分候选。

### 2.2 嵌入（Embedding）：让"按意思搜代码"成为可能

符号表回答的是"你知道名字"的问题。但经常你**不知道名字**，只知道"处理图片输入的那段代码"。这时关键词搜索很无力——你得猜标识符。

**嵌入模型**（aide 默认用 bge-m3，通过 Ollama 本地跑）把每段代码变成一个**向量**——一个 1024 维的数字数组。它的神奇之处在于：**意思相近的文本，向量距离也近**。"权限弹窗"这段中文描述，和写着 `PermissionDialog` 的英文代码，在向量空间里是邻居。

于是语义搜索变成一道几何题：把你的问题也变成向量，在向量数据库（aide 用 Qdrant Edge，本地嵌入式）里找最近邻。不需要任何关键词匹配。

两条层级的关系：

```
结构层（tree-sitter）：精确，"名字 → 位置/关系"，但你要知道名字
语义层（embedding）：模糊但聪明，"意思 → 候选代码"，不知道名字也能搜
```

### 2.3 索引的生命周期

- **全量构建**：遍历项目 → 解析 → 符号表+边表落盘（`symbols.json`/`edges.json`）→ 代码片段嵌入进向量库。分两阶段：结构层秒就绪，嵌入后台慢慢跑
- **增量更新**：保存文件时只重建那一个文件；`git pull` 后手动触发 rescan
- **失效重建**：切换嵌入模型/维度（向量空间不兼容）、索引格式升级（比如缺 `edges.json`）→ 自动全量重建

## 3. MCP 工具：agent 的"手"是怎么长出来的

### 3.1 工具调用的本质

大模型本身不会执行任何操作。它能做的是**输出一段结构化的"我想调用 X 工具，参数是 Y"的文本**。harness（Claude Code SDK）看到这段文本后：真正去执行 → 把结果喂回给模型 → 模型继续写。

**MCP（Model Context Protocol）** 是定义"工具怎么注册、怎么被发现、怎么被调用"的协议。aide 的 sidecar 用 SDK 的 `createSdkMcpServer` 在进程内注册了三个工具：

| 工具 | 回答的问题 | 替代什么 |
|---|---|---|
| `find_symbol` | X 定义在哪？（精确） | Grep 找定义 + Read 确认 |
| `call_graph` | 谁调用了 X / X 调用了谁？ | Grep 全部用法 + 逐条人工分辨 |
| `semantic_search` | 做某件事的代码在哪？（按意思） | 猜关键词反复 Grep |

模型在会话开始时收到工具列表（名字+描述+参数 schema），之后它"决定"何时使用——**"决定"这个词是整个故事的关键，见第 4 节**。

### 3.2 aide 里的完整链路

工具不在模型进程里，也不在 Claude 服务器上——它在 aide 自己的架构里跑：

```
模型（Kimi/Claude API）
  ↕ SDK（claude.exe 子进程）
  ↕ sidecar（Node 进程，注册 MCP 工具；工具被调用时发 codegraph_query 事件）
  ↕ Rust（Tauri 后端，持有索引；查询后回写 codegraph_result）
  ↕ sidecar 把结果格式化成紧凑文本 → 模型
```

设计约束值得一提：**不开端口、不新增进程**——工具调用和应答全走 sidecar 已有的 stdin/stdout 管道，用的是权限弹窗同款的 request/response 模式。

## 4. 工具采纳率：为什么模型会"无视"工具（本项目的核心战场）

工具注册成功 ≠ 模型会用。这是我们花了一整天实测出来的，也是最容易被忽视的一类失败——**没有任何报错，agent 就是不用**。

### 4.1 实测发现

- 工具在模型的工具列表里（实锤 `status: connected`），prompt 里**直接命令**"用 find_symbol"，模型照样 Grep（2026-07-26 headless 实验）
- 原因：编码模型的训练数据和系统提示里，"探索代码 = Grep/Read"是根深蒂固的模式。一个没见过的新工具，在模型的决策里优先级天然垫底
- 第三方模型（本项目用户跑的是 Kimi K2.6，不是 Claude）对"请自觉"类引导的服从度更不稳定——同样的引导，这轮用下轮不用

### 4.2 三层引导机制（按强制力从弱到强）

| 层 | 机制 | 性质 | 实测效果 |
|---|---|---|---|
| **L1 工具描述+instructions** | 工具注册时附带的使用规则文本，会话开始即呈现 | 模型**自觉** | 0 → ~10% 采纳率 |
| **L2 skill** | 写一个"探索代码必读"的 skill 进技能列表，靠 harness 的"匹配任务必须调用技能"纪律触发 | 模型**自觉**（只是纪律更强） | 对 Claude 有效；对 Kimi 进了列表也不主动调 |
| **L3 PreToolUse hook** | harness 级拦截：每次模型 Grep 一个符号状 pattern，hook 强制执行并注入"该用索引工具"的提示 | **模型无法忽略**（每次 Grep 都会被贴脸提醒） | Read 13→2，成本 -30%，skill 也被带动触发 |

教训凝练成一句话：**对"请模型配合"这类需求，凡能下沉到 harness 强制层的，不要停留在提示层。**

### 4.3 输出质量决定留存

模型用了一次工具之后**还愿不愿意继续用**，取决于第一次拿到什么：

- 返回精确位置 → 正循环，继续用
- 返回"没找到"（尤其是因为我们索引有覆盖缺口或名字形式不匹配）→ 模型学会"这工具不好使"，弃用

两个真实案例：模型查 `PermissionDialog` 空命中——因为 Vue 的 `<script setup>` 组件不声明具名符号，组件名只在文件名上（修复：按文件名合成组件符号）；查 `PermissionManager.makeCallback` 空命中——索引按裸名建键不认限定名（修复：查询统一取叶段）。**每一次空命中都是产品反馈，要么索引该补覆盖，要么查询该做归一化。**

## 5. 怎么验证：不看感觉，看数据

这套系统配有完整的验证工具链（都在 `agent-sidecar/`）：

1. **`smoke-mcp.ts`**：验证"注册层"——工具是否真的出现在模型的工具列表里
2. **`smoke-runtime.ts`**：验证"行为层"——驱动真实的打包 sidecar 跑真实 prompt，输出工具调用直方图（几次 find_symbol、几次 Grep、几次 Read）
3. **转录取证**：会话转录在 `~/.aide/claude/projects/<项目>/`，可以精确统计每次工具调用和返回内容

任何引导文案/机制的改动，都必须过 smoke-runtime 看直方图变化，而不是"感觉应该有用"。

## 6. 术语速查

| 术语 | 一句话 |
|---|---|
| AST / 语法树 | 代码的结构化表示，tree-sitter 的产物 |
| 符号（Symbol） | 有名字的定义：类/方法/函数/接口/枚举/字段 |
| 调用边（CallEdge） | "A 在某行调用了 B"的记录 |
| 嵌入（Embedding） | 把文本变成向量，意思相近则向量相近 |
| 向量数据库 | 存向量并按距离检索最近邻的库（Qdrant Edge） |
| MCP | 模型上下文协议，定义工具如何注册和调用 |
| sidecar | aide 的 Node 进程，夹在 SDK 和 Rust 之间跑 agent 会话 |
| hook（PreToolUse） | harness 在工具执行前强制运行的回调，可注入提示或拦截 |
| skill | 任务级技能包，模型遇到匹配任务时被引导调用 |
| 采纳率 | 模型在"该用工具的场景"实际使用工具的比例 |
