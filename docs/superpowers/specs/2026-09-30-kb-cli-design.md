## 1. 背景与问题

### 1.1 现场（2026-09-30）

一台按文档部署的实例（WSL，compose 项目 `heaven`）升 0.5.0 失败：用户执行了面板给出的那条命令

```
docker compose pull knowledge && docker compose up -d knowledge
```

pull 成功、up 成功、**退出码 0**，但容器没重建、服务端仍是 0.4.0，面板继续提示"服务端太旧"。用户重复执行、重复无效。

原因：该机器 `.env` 里有一行 `KB_IMAGE=…:0.4.0`（2026-09-21 升 0.4.0 时留下的 —— 当时交付的 compose 默认标签还停在 0.3.0，**不钉就升不上去**）。版本号标签**不可变**，于是 pull 拉回同一个镜像、`up -d` 看 digest 没变、不重建。全程无任何报错。

### 1.2 根因：能解释的看不见，能看见的不解释

- 那条命令**没有坏**：`.env` 说"钉在 0.4.0"，它就忠实执行到底；
- **能解释的（面板）看不见 `.env`** —— 客户端只有 HTTP，观测到的只有 `/api/health` 的 `version` 一个比特，永远看不到宿主上的文件；
- **能看见的（compose）不负责解释** —— 它只服从配置，不告诉用户"你被配置挡住了"。

用户被夹在中间：面板说"该升级"，配置说"待在 0.4.0"。**修法不是把矛盾翻译给用户看（让他当排障员），而是让能看见配置的那一方自己去做决定。**

### 1.3 附带发现：交付面有三处在撒谎

| # | 撒谎 | 证据 |
|---|---|---|
| 1 | README 让用户「`cp .env.example .env`，改 `DB_PASSWORD`」 | `.env.example` 里**没有** `DB_PASSWORD` 这一行 |
| 2 | `.env.example` 列了 10 个旋钮 | compose 只接了 **2 个**（`DB_PASSWORD` / `KB_CORS_ALLOWED_ORIGINS`）；其余 8 个（含安全相关的 `KB_ALLOWED_CIDR`）写进 `.env` 也进不了容器 |
| 3 | `.env` 里写 `KB_IMAGE` 是"钉版本" | 实际语义是**静默冻结**：面板的升级命令从此永远无效（§1.1） |

第 2 条尤其危险：一个以为配了 `KB_ALLOWED_CIDR=192.168.1.0/24` 就把服务关进内网的管理员，实际上**服务对整个网络敞开**。

### 1.4 影响面：不只是这一台

凡在 0.4.0 发布期按指导升级过的机器，`.env` 里都留着同一个钉 —— 这批用户全部卡在"命令跑了没用"，且看不出为什么。

## 2. 目标与非目标

### 2.1 目标

1. **用户零输入**：跑一条命令，不回答任何问题、不编辑任何文件。
2. **用户只保管一个文件**：`aide-kb`。
3. **不可能再静默失败**：每一步的成败都在输出里，退出码如实。
4. **存量部署被接管**：既有 `.env` / compose / 卷继续用 —— 数据不动、密码不换、项目名不换。
5. **用户看到的旋钮都真的生效**：交付面上不存在"配了没用"的键。

### 2.2 非目标

- **不做常驻自动更新**（watchtower / docker socket 自升级）：代价是把宿主 root 交给容器，且版本前进不再由人决定。留作后续（§12）。
- **不做 Windows PowerShell 版**：只做 bash（WSL / Git Bash 可用）。
- **不做 `config` / `backup` 子命令**：备份是 `upgrade` 的内建步骤；改配置的受支持路径是编辑脚本生成的 `.env` 后重跑。
- **不改知识库服务端本身**：本次只动部署入口与文档。

## 3. 已拍板的决策

| # | 决策 | 理由 / 代价 |
|---|---|---|
| D1 | 安装时**什么都不问**：密码自动生成、端口自动选、网段默认不限 | DB 端口不映射到宿主、只在 compose 网络内可达 → 用户永远不需要知道这个密码；让他输入反而是 28P01 那类事故的来源 |
| D2 | 范围 = **装 / 升 / 查** | YAGNI；其余交给 docker 原生命令与文档 |
| D3 | **只做 bash** | 客户那台跑 compose 的机器本就是 linux 形态；双份逻辑（.sh + .ps1）是同步负担 |
| D4 | **单文件自包含**（compose 内嵌在脚本里） | 用户保管物从 3 个降到 1 个；且"用户手改配置"这条路**物理上不存在** |
| D5 | 备份**永不自动删**，但每次运行结束打印备份位置与删除命令 | 删用户的东西必须由用户决定；但既然不删，就得让他知道东西在哪、怎么清 |
| D6 | `./aide-kb` 无参数**直接做**（不弹 y/n） | 跑这条命令的意图就是升级；备份已在前兜住；弹问会把"一条命令"退回"一次交互" |
| D7 | `.env` 的 `KB_IMAGE` = **脚本的输入（目标版本），不是用户的把手** | 见 §6.4 —— 这条直接消灭 §1.1 那个坑 |

## 4. 形态与入口

交付物：**`aide-kb`**（bash，可执行）。用户把它放在部署目录里，与它生成的 `docker-compose.yml` 同级。

| 命令 | 行为 |
|---|---|
| `./aide-kb` | 没部署 → **装**；有部署 → **升到最新**（目标重置为 `:stable`，无条件摘钉） |
| `./aide-kb status` | 当前版本（镜像 tag + 服务端自报）、项目名、部署目录、端口、是否钉版、备份目录与最近一次备份、健康状态 |
| `./aide-kb upgrade [版本]` | 显式升级；给版本号 = 切到那一版（官方回滚手段） |

**文件所有权**（"用户不碰配置"的物理保证）：

- `docker-compose.yml` —— **脚本托管**。发现被手改过 → 备份为 `.bak` 再覆盖，并在输出里说明。
- `.env` —— **脚本的产物，只补不覆盖**：安装时生成（随机密码 + 中文注释），之后每次运行只补缺失键，**绝不覆盖已有值**。这条同时是接管既有部署的安全前提（§6.1）。
- `backups/` —— 只增不减（D5）。

## 5. 首次安装

```
前置检查 → 探端口 → 生成密码 → 写 .env + compose → pull → up -d → 探 health → 报结果
```

### 5.1 前置

`docker` 与 `docker compose`（v2）可用；镜像仓可达且已登录。镜像仓是私有的，新机器需要一次 `docker login <ACR 域名>`（凭证由我们发放）。

脚本**不做独立的登录探测**，而是在 `pull` 失败时把"很可能是没登录"作为**首选解释**给出来 —— 这比猜登录态可靠。

### 5.2 探端口

默认 8788；被占用则顺延（bash `/dev/tcp` 连接测试，零依赖）。

**只在全新安装时探测**：已有部署一律沿用 `.env` 里的值 —— 否则会把自己的端口当成"被占用"而改掉。

### 5.3 生成密码

`/dev/urandom` 取 32 位 **hex**。只含 `0-9a-f` 是因为它会被拼进 `KB_DB_URL` —— 用 base64 就得处理 URL 转义。

### 5.4 写 `.env`

只写**真实生效**的键，一个不多：

| 键 | 何时写 |
|---|---|
| `DB_PASSWORD` | 生成时写死；接管时**沿用既有值** |
| `KB_HOST_PORT` | 端口顺延过才写；否则省略（compose 默认 8788） |
| `KB_CORS_ALLOWED_ORIGINS` | 省略即用 compose 默认（已含桌面端三种形态） |
| `KB_IMAGE` | 只有 `upgrade <版本>` 写过；`./aide-kb` 无参数会摘掉它 |

带中文注释说明每一项是什么、什么时候才需要改。

### 5.5 收尾输出

```
装好了：服务端 0.5.0。
在 aide 面板打开知识库 → 填地址 http://<本机IP>:8788 → 第一次会让你建管理员。
```

### 5.6 失败必出声

任何一步失败 → 打印「哪一步 / 失败的原样命令 / 下一步怎么办」，退出码非 0。

## 6. 升级与接管

### 6.1 接管既有部署：三条沿用规则

**接管判据**（三者取一，都算"这个目录里已有部署"）：当前目录存在 `docker-compose.yml`；或存在 `.env`；或本目录对应的 compose 项目已有容器（`docker compose ps -a` 有输出）。判定后进入接管模式，三条规则各自对应一个已实锤的事故：

| 沿用 | 不遵守的后果 |
|---|---|
| `.env` 里的 `DB_PASSWORD` | `pgdata` 已用它初始化过（`POSTGRES_PASSWORD` 只在首次初始化生效）→ **28P01，无限重启** |
| compose **项目名** | 项目名决定卷名（`heaven_pgdata` 来自目录名）→ 换名字 = 起一套**空库**，用户以为数据丢了 |
| 端口 / CORS | 面板连不上 |

旧的 `docker-compose.yml` 备份为 `.bak` 后写入脚本托管版。

### 6.2 升级序列

```
确保 db 起来（up -d db，等 healthy）→ 备份 → pull → up -d → 探 health → 打印版本变化
```

- **先确保 db 起来**：栈可能被 `down` 过，而备份要用它（db 要 `pg_dump`，附件要从 knowledge 容器里取）。
- **备份**：`<部署目录>/backups/<时间戳>/` 下 `db.sql`（`pg_dump`）+ `storage.tar.gz`（容器内 `tar` —— 已验证 debian-slim 自带 GNU tar 1.34，**不需要额外拉镜像**）。**备份失败 → 中止升级**：迁移是单向的，备份是唯一的后悔药。
- **幂等**：记录运行中容器的镜像 ID → pull → 比对。相同 → 打印「已是最新（0.5.0），没动任何东西」，**不备份、不重建、不产生新目录**。这条与 D5 是一对：既然备份永不自动删，"没升级也备份"就会把 `backups/` 无意义地撑大。

### 6.3 跨目录保护

当前目录没有部署、但机器上已有别的 aide-kb 部署（按容器 label `com.docker.compose.project.working_dir` 与镜像名匹配）→ **不静默装第二套**，打印那个目录并建议去那里跑。

### 6.4 目标版本语义（消灭 §1.1 那个坑）

- `./aide-kb`（无参数）→ 目标 = `:stable`（最新）→ **无条件摘钉**；
- `./aide-kb upgrade 0.4.0` → 目标 = `…:0.4.0`，写进 `.env` 的 `KB_IMAGE` 后走同一条路；
- `.env` 的 `KB_IMAGE` 是**脚本的输入**，不是用户的把手 —— 用户从此不需要知道它存在；
- 刻意钉住不动的用户：`status` 明确告诉他「你钉在 0.4.0（低于客户端要求的 0.5.0），面板会一直提示升级」。

## 7. 数据安全红线

写进脚本头部注释，同时是实现的硬约束：

1. **绝不 `down -v`、绝不删卷**。README 里"永远别加 `-v`"从此是物理保证，不再只是纪律。
2. **接管必沿用密码与项目名**（§6.1）。
3. **备份失败 → 中止升级**。
4. **备份永不自动删**（D5），只在输出里给删除命令，形如：

   ```
   备份：backups/2026-09-30-1340/（db.sql 12 MB + storage.tar.gz 3 MB）
   清理旧的：rm -rf backups/2026-09-30-1340
   ```

## 8. 验证链

三级回退，全部零依赖，**不要求宿主装任何东西**：

1. 宿主 `curl` → 2. 宿主 `wget` → 3. **容器内 `bash /dev/tcp`**（已实测通过：`exec 3<>/dev/tcp/127.0.0.1/8788` + 手写 HTTP 请求）。

收尾三态，都不许含糊：

| 情形 | 输出 | 退出码 |
|---|---|---|
| 版本变新 | `0.4.0 → 0.5.0` | 0 |
| 服务端没有 `version` 字段 | 「这是 0.5.0 之前的服务端」 | 0 |
| 起来了但版本没变 | 为什么（多半是被钉住 / 远端没更新） | 非 0 |

## 9. 脚本与仓库 compose 的一致性守卫

脚本内嵌一份 compose 模板，仓库里 `knowledge-server/docker-compose.yml` 也有一份（`docker-compose.dev.yml` 与开发流程依赖它）。两份必漂移 → **构建期守卫**，仿项目既有的 `check:lsp-parity` / `check:sync-io`：新增 `scripts/check-kb-compose-parity.mjs`，提取脚本中哨兵行之间的内容与仓库文件比对，不一致即报错。

compose 模板本次有一处实质改动：宿主端口从硬编码 `8788:8788` 改成 `${KB_HOST_PORT:-8788}:8788` —— 端口顺延需要它。

## 11. 测试策略

冒烟脚本（仿 `knowledge-server/smoke.sh`：`set -euo pipefail` + 明确前置 + 打印跳过原因），用**本地 dev 镜像**在临时目录跑：

1. 首次安装（零输入）→ `status` 报出版本；
2. **接管既有部署** → 断言生成的 compose **项目名一致、密码未被换**（这两条是事故防线，必须有用例）；
3. **幂等** → 已是最新时不重建、**不产生新备份目录**；
4. 端口被占 → 顺延；
5. **备份失败 → 中止升级**（只读目录模拟）；
6. `upgrade 0.4.0` → `.env` 里出现 `KB_IMAGE`。

工程约束：

- **只用 bash 3.2 特性**（macOS 自带 bash 就是 3.2）。用关联数组之类会让 macOS 上直接跑不起来 —— "linux/macOS/WSL 都能跑"就成谎话。
- 测试要能离线跑，脚本顶部留一个**镜像仓**注入点：`AIDE_KB_IMAGE` = 仓库引用**不含标签**（默认 `registry.example.com/aide/aide-knowledge`）。目标镜像一律是 `${AIDE_KB_IMAGE}:${标签}`，标签取 `stable`（无参数）或用户给的版本号。`.env` 里落盘的 `KB_IMAGE` 则是**完整引用（含标签）**，因为 compose 直接用它。这是**为测试存在的接口**，不藏着。

## 12. 未决与后续

1. **脚本会腐坏**。交付出去的脚本改不了，而面板话术与 app 一起升级。对策是把脚本做薄：只做"读写配置 / pull / up / 探 health"这类**不随产品版本变化**的动作；"跨版本的特殊步骤"一律放镜像侧（服务端自己跑迁移）。真需要改脚本时，由面板提示「重新取一次 `./aide-kb`」。
2. **常驻自动更新**（原方案 B）：代价是给容器 docker socket（= 宿主 root）、且版本前进不由人决定。本设计不挡它 —— 到时候只是给 `./aide-kb` 套一个定时器/监听器。
3. **Windows 宿主**：无 bash 时怎么办（Git Bash / WSL 可用；纯 PowerShell 不支持）。
4. **ACR 凭证发放流程**：本次只把"没登录"的报错说清楚；凭证怎么发给客户是另一件事。
