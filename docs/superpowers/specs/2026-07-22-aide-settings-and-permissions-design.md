# Aide 独立设置与工具权限体系设计

**日期：** 2026-07-22  
**状态：** 已完成设计评审，待用户审阅书面规格

## 目标

Aide 必须独立维护自己的设置与权限规则，不能依赖 Claude Code CLI 的 `.claude/settings.json` 读写与规则解释。用户应通过 Aide 的主题化设置 UI 管理全部可持久化配置；JSON 是底层存储与迁移格式，不是日常配置入口。

本设计同时解决：

- 现有“总是允许”通过 SDK 建议写入 `.claude/settings.json` 的外部依赖；
- Auto 模式安全分类器临时不可用时，预先匹配的安全规则仍被阻塞；
- `config.json` 中的配置逐步增多、缺乏统一 schema/作用域/迁移模型；
- 用户无法理解或安全地手工编辑设置 JSON。

## 非目标

- 不实现或调用 Claude Code 的 `.claude/settings.json` 规则格式。
- 不提供原始 JSON 编辑器作为常规设置界面。
- 不把 API Key、Token、密码等秘密写入任何 `.aide/settings*.json`。
- 不重做现有 SettingsPanel 的整体视觉体系。
- 不将 provider 特有权限字段加入 provider-agnostic IPC 核心协议。

## 配置文件与作用域

Aide 的统一配置采用同一 schema，但根据作用域存储在不同位置。

| 层级 | 文件/来源 | 用途 | 可编辑性 |
|---|---|---|---|
| 受管策略 | 管理员提供的策略来源（实现时确定平台路径） | 组织强制限制 | 只读 |
| 用户全局 | `~/.aide/settings.json` | 所有项目的个人偏好与规则 | 可编辑 |
| 项目共享 | `<project>/.aide/settings.json` | 可提交 Git 的项目规则 | 可编辑（项目可写时） |
| 项目本地 | `<project>/.aide/settings.local.json` | 仅本机、通常不提交 Git 的覆盖 | 可编辑（项目可写时） |
| 会话临时 | 内存 | 本会话一次性/临时选择 | 只读展示，随会话结束失效 |

生效顺序固定为：

```text
受管策略 → 用户全局 → 项目共享 → 项目本地 → 本会话临时
```

上层明确的 `deny` 不能被下层 `allow` 放宽。若多个同层规则匹配，匹配条件更具体的规则优先；若具体度相同，按稳定规则顺序解析，避免非确定性。

## 配置 schema 与敏感数据

统一 schema 带 `schemaVersion`，并覆盖所有当前及未来可持久化的 Aide 设置：通用偏好、快捷键、Provider 的非敏感配置、扩展/市场状态、CodeGraph、JDK、工作区 UI 状态与权限规则。

每个持久化字段必须有一个设置描述符，声明：

- 唯一字段 ID 和默认值；
- 存储类型与校验规则；
- 支持的作用域；
- 对应 UI 所有者；
- 是否敏感；
- 是否允许项目级覆盖。

这一描述符目录是“任何落盘字段均有 UI 入口”的完整性边界。保存实现不得丢弃安全的未知字段，保证新版本或插件添加字段时旧版本不会静默擦除数据。

秘密值迁移至操作系统安全凭据存储。设置 JSON 仅保存安全引用或“已配置”状态；UI 不回显明文。

## 迁移

Rust 设置模块在应用启动时处理一次性迁移：

1. 读取旧 `~/.aide/config.json`；
2. 按 `schemaVersion` 转换为统一设置 schema；
3. 用临时文件 + rename 原子写入 `~/.aide/settings.json`；
4. 仅在新文件写入成功后，将旧文件标记为迁移备份；
5. 后续运行只读取和写入新设置体系，禁止长期双读双写。

迁移必须幂等。所有磁盘读写、序列化和目录处理必须使用 `async fn + spawn_blocking`，不允许阻塞 Tauri 主线程。

## 权限规则

权限规则是 provider-agnostic 的工具策略。规则至少包含稳定 ID、效果、目标工具及可解释的可选匹配条件：

```text
effect: allow | ask | deny
target: 工具名称 + 可选命令/路径等条件
scope: managed | user | project | local | session
```

UI 只暴露可理解的条件：

- Bash：全部命令、命令前缀、包含文本；
- 文件工具：全部路径、文件夹及子文件；
- 其他工具：工具本身或经过审核、可解释的关键字段。

规则例如：“在此项目中，执行以 `pnpm test` 开头的 Bash 命令时，始终允许”。不要求用户理解 glob、SDK `PermissionUpdate` 或 Agent SDK 的 permission mode。

## 执行架构

Rust 负责配置存储、迁移、校验、分层合并和生成有效权限策略快照。权限策略必须通过 provider-agnostic 的 sidecar 协议交给当前活动会话；字段只表示通用工具策略，不加入 Claude 专属概念。

sidecar 在工具请求前执行以下顺序：

1. 匹配有效 Aide 权限策略；
2. 命中 `allow`：直接放行，不请求 SDK/Auto 分类器；
3. 命中 `deny`：直接拒绝并提供可解释原因；
4. 命中 `ask`：沿用现有权限请求事件与主题化确认 UI；
5. 未命中：完全回退到会话现有 permission mode 与 provider/SDK 默认逻辑。

规则变更保存成功后立即重算并下发快照，无需重启应用或会话。已在等待用户确认的旧请求不被事后自动结算；更新仅影响其后的工具调用。

Claude 专属的 `canUseTool` 与 SDK 适配继续留在 `agent-sidecar/`。前端和 Rust 只认识通用的工具策略快照与现有统一 ChatEvent/SidecarCommand 协议。

## 设置 UI

保持 `SettingsPanel` 的现有导航、对话框、滚动容器和既有栏目：

```text
通用 / 模型 / 权限 / 扩展 / 市场 / 代码索引 / Java
```

新增“权限”栏目。视觉稿位于：

- `docs/superpowers/design-previews/2026-07-22-permission-settings.html`

权限页包含：

- 用户全局、项目共享、项目本地、受管策略作用域页签；
- 当前作用域真实存储位置及可编辑状态；
- 规则卡片：工具、匹配摘要、allow/ask/deny 效果、来源；
- 对受管策略的只读状态；
- 新增、编辑、删除规则；
- 被更高优先级规则遮蔽时的原因；
- 对某项调用的最终决策与命中规则链的解释入口；
- 未打开项目或目录不可写时禁用对应作用域并说明原因；
- 保存成功/失败的即时主题化反馈。

新增/编辑规则复用 `useModal`，删除使用 `useModal.confirm`，短暂反馈使用 `useToast`，选择控件使用 `ThemedSelect`，图标使用 `Icon`。规则编辑组件必须作为独立 `settings/permissions/` 模块，不把业务逻辑内联进 `SettingsPanel.vue`。

所有颜色、背景、边框、阴影、圆角和间距使用现有 `--aide-*` token。不得新增独立配色，也不得硬编码颜色。必须在 warm-dark、catppuccin 与 glass 主题下验收。

现有设置栏目继续各自承载对应编辑 UI；统一 schema/描述符只保证每个实际落盘字段有明确 UI 所有者与支持作用域，而非将所有设置压入一个页面。

## 错误处理

- 前端先做表单校验，Rust 做权威校验；失败时不修改有效策略快照。
- 写入失败（权限、磁盘、杀毒锁）时不可显示成功；保留编辑值，给出可重试的主题化错误反馈。
- 项目未打开或路径不可写时，禁用项目作用域，但允许继续编辑用户全局设置。
- 受管策略不可编辑、删除或通过低层规则放宽。
- 对 provider 特有能力使用扩展字段隔离，不污染通用规则 schema。

## 测试与验收

### Rust

- `config.json` 到 `settings.json` 的迁移、幂等性与成功后备份；
- 不同作用域合并；
- 上层 `deny` 不能被低层 `allow` 覆盖；
- 规则具体度与稳定顺序；
- 原子写失败时原文件和有效快照保持不变；
- 设置描述符覆盖所有可持久化字段。

### sidecar

- `allow` 命中不调用 SDK/Auto 分类；
- `deny` 命中拒绝且给出原因；
- `ask` 命中发送现有权限请求；
- 未命中保持现有 permission mode 行为；
- 活动会话收到更新策略后，下一次调用使用新规则。

### 前端

- 作用域切换、规则新增/编辑/删除；
- 受管规则只读；
- 遮蔽和最终生效原因；
- 项目不可写、保存失败与保留表单状态；
- 设置描述符与 UI 所有者的完整性检查。

### 人工验收

- warm-dark、catppuccin、glass 切换后权限页全部重配色；
- 添加 `pnpm test` 的 Bash allow 后，即使 Auto 分类服务不可用，匹配命令仍可放行；
- 非匹配 Bash 命令仍按原 permission mode 处理；
- 删除规则后下一次调用立即按默认路径处理；
- 原有 Provider 设置、工作区布局及普通偏好迁移后不丢失。

## 实施边界

实现时应优先建立独立设置/策略模块与清晰的数据边界；不可在既有组件或 `permissions.ts` 中补丁式塞入配置读写。具体文件拆分、协议变更顺序、迁移步骤和测试命令在下一阶段实施计划中确定。
