## 1. 问题

**会话变更这个能力其实挺好，但它没被看见。**

它现在唯一的入口是右栏纵栏里 8 分之 1 个图标（`src/App.vue:341`，`变更 (Ctrl+2)`）。
信号其实已经在屏幕上——那一项本来就带角标——但它待在视线边缘，且不说明自己是什么。
而用户做"这轮我接不接受"这个决定的时候，人不在那儿：他在读回答，视线在对话流底部。

同一份信息在别处也缺一句话。对话流里是 **N 张各自摊开的变更卡**
（`src/components/ChatMessage.vue:149` 对变更类工具一律 `default-expanded`），
它们回答"这一处怎么改的"，但**没有任何东西回答"这一轮一共改了什么"**。

### 目标

让会话变更在**决策点**上可见：

| 原则 | 落法 |
|---|---|
| 信号落在决策点上 | 卡片挂在消息流尾部——你读完回答、正想"接下来呢"的那一秒，它就在那儿 |
| 先给规模，再给内容 | 一张卡先给"几个文件、多少行、偏加还是偏删"；想细看再展开 |
| 自带下一步 | 展开 = 本轮清单；`变更面板 ↗` = 完整台账 |

### 成功判据

1. 一轮改完文件后，**不打开任何侧栏**，就能说出这轮改了几个文件、大致改了多少行。
2. 想知道"这一个文件改了什么"时，从卡片到达 diff 不超过两次点击。
3. 想找"这个会话一共改了什么"，从卡片上有常驻可见的入口。
4. 长会话里连续几十轮，卡片**不累积成视觉噪音**（无变更的轮不渲染、收起态只有两行）。

## 2. 形态规格

原型页 `docs/prototypes/2026-09-24-turn-change-footer.html` 是**视觉与状态流转的唯一依据**，
其 CSS 直接取自 `var(--aide-*)` 语义 token（值抄自 `src/themes/glass.ts`），可整体搬进组件。
该页 §01「生命周期」是"同一个位置、四种形态"的逐帧对照（含"第一个文件落下才出现"那一刻），
§02 把"往回翻看不到历史卡"这个代价画成了实图——**形态争议以原型为准，语义争议以本文为准**。

### 2.1 结构（两行）

```
┌──────────────────────────────────────────────────────────────┐
│ 本轮变更                                变更面板 ↗  [展开 ▾] │  行 1 = 身份 + 动作
│ 4 个文件   +203 −2                    [——— 比例条 ———]        │  行 2 = 全部统计量
└──────────────────────────────────────────────────────────────┘
```

**行 1 / 行 2 的分工是硬约束**：行 1 只放身份与动作，行 2 只放统计量。
理由（评审依据）：`4 个文件` 与 `+203 −2` 是**同族信息**——都是"这一轮有多大"，
只是量纲不同（文件数 / 行数）。拆到两行是把同类割开；而把统计量塞进行 1 则会
让"身份 + 一个统计量"混装（原型页 §02 的 ①/②/③ 三案并排可对比）。

### 2.2 视觉规格

| 元素 | 规格 | 依据 |
|---|---|---|
| 卡面 | `bg-base` + `radial-gradient(accent-subtle)` 左上泛光 + `accent 24%` 描边 + `highlight-inset` | 用**颜色**区别于灰调的过程胶囊，不用体量 |
| 卡名 | 10.5px / 600 / `letter-spacing:1.1px` / accent | 拉字距才立得住 |
| 行数数字 | 19px / 600 / mono / `letter-spacing:-.02em` / `tabular-nums` | 大数字必须收字距才"紧"；等宽保证展开收起不跳位 |
| 文件数 | 13px（数字 14px mono 600） | 与行数同族的次级量，**不是注释**——12px 委屈它 |
| 比例条 | 5px 高 / `gap:1.5px` / `min-width:2px` / 圆角 99px / 轨道 `surface-hover` / `flex:0 1 230px` 贴右端 | 见 2.4 |
| 展开按钮 | 圆角胶囊 + 细边 + `surface-default`，hover 变亮 | 一行小字当入口是"小气"的主要来源 |
| 展开箭头 | border 三角（同 `ProcessGroup`）旋转 90° | 字符 `▾` / emoji 换字体就变形 |
| 面板入口 | 11px / accent / 无底无边 / hover 下划线 | **沿用变更卡头部 `打开 ↗` 的既有形制**（`ChangeFileList` 同款小动作），不是新发明 |
| 悬停 | 只动 accent 透明度与底色，**不加边框、不改尺寸** | 边框变化会改变盒模型让整卡"抖" |
| 展开体 | `bg-deep` + 细边，内放 `ChangeFileList` | 见 §4 复用面 |

### 2.3 交互

| 动作 | 行为 |
|---|---|
| 点卡片上任意**非按钮**区域（含卡名、空白、统计行） | 展开 / 收起清单 |
| `展开 ▾` / `收起 ▴` | 同上（胶囊按钮，视觉出口） |
| `变更面板 ↗` | 右栏**确保显示** changes tab（见下） |
| 展开后的文件行 | 点行 = 打开该文件 diff（`useDiffWindow().openDiff(row, wsRoot)`） |
| 文件行 hover 出的图标 | 在编辑器打开 / 撤回此文件（与面板行为一致） |

### 2.3.1 `变更面板 ↗` 必须走「确保显示」，**禁止用 `select()`**

`useRightPanel.select()` 是 **toggle**（`src/composables/useRightPanel.ts:44-53`）：
用户**已经**在变更 tab 时点它，会把面板**收起来**——一个"给我看看"的请求变成"把你的面板关掉"。

这不是新坑：`ensureBrowserShown()`（`useRightPanel.ts:75-79`）就是为同一个坑存在的，注释里
写着原话。落法二选一：

- **推荐**：把该特例泛化成 `ensureTabShown(id: RightTabId)`（`tab = id; collapsed = false;`
  + browser 的懒挂载分支），`ensureBrowserShown` 改为它的薄封装。既去掉一个特例，
  也给本卡一个语义正确的入口；
- 或者在卡片里按同样三行手写一遍。

**判据（验收用）**：已经在变更 tab 且面板展开时点 `变更面板 ↗`，面板**不得收起**。

### 2.4 比例条的语义（易错点，必须守住）

**长度恒定，只让绿/红分割表达"偏加 / 偏删"。量级由数字承担。**

- 条若随数字宽度或改动量伸缩，读起来像"长度 = 改动量"——**假信号**。
  真按量级做就需要一个会漂移的参照（本会话最大轮），而那个参照在翻历史时会**回溯缩放**。
- **条右端不挂任何文字**。紧挨着条的标签会被读成"条在量它"——
  把 `4 个文件` 贴在条右侧，等于说"这根条量的是文件数"，而条表达的是增删比例，与文件数无关。
- 轨道必须用 `surface-hover`（`surface-default` 太淡）：纯新增轮会变成一根凭空浮着的绿线。
- `gap:1.5px` 让两段不糊成一条；`min-width:2px` 保证 `−1` 行也看得见。

### 2.5 文案规则

| 情形 | 文案 |
|---|---|
| 文件数 | `1 个文件` / `4 个文件` / `12 个文件`（量词随数走，不留 `N 个文件` 的生硬） |
| 增删 | `+203` `−2`（**零值不渲染**：`−0` 整项消失，纯新增文件只显示 `+64`） |
| 数字格式 | 千分位仅 ≥4 位时出现（`+1,240`），且按最宽情形的列宽预留 |
| 进行中 | `正在改`（替代卡名） |
| 面板入口 | `变更面板 ↗`（固定文案，不随轮次变） |

## 3. 状态机

| 状态 | 触发 | 渲染 |
|---|---|---|
| **隐藏** | 该轮 `files` 为空 ——**进行中同样适用** | **整卡不渲染**（不渲染成"0 个文件"，也不占位）。`正在改 · 0 个文件` 这种状态不存在：卡片**在第一个文件落下时才出现**，这一刻的"出现"自带信息量（"开始动我的文件了"） |
| **进行中** | `sessionState[sid] === "running"` 有 pending 轮，且 `files.length ≥ 1` | 卡名 `正在改` + 呼吸点（`prefers-reduced-motion` 下停），统计行实时更新。**无面板入口、无展开**——这轮还没结束，"账单"还不存在，给入口等于让人点进半成品 |
| **已结算** | `solidifyRound` 落定 | 卡名 `本轮变更`，`变更面板 ↗` 与 `展开 ▾` 出现 |
| **首次发现** | 本会话首次出现有变更的轮 | 整卡淡入 + accent 描边微亮一次，随后归于安静（一次性，不常驻动效） |

进行中的数据来源现成：`file-tree-changed` 事件已驱动实时 drain
（`src/composables/useConversationChanges.ts:251 attachLiveRefresh`、`:269 scheduleLiveRefresh`），
无需新增订阅。

**单一事实源**：卡片读的就是面板读的同一份 `rounds`（`App.vue:322` 的 `useConversationChanges`

| 需要 | 直接复用 |
|---|---|

| 本轮文件行 | `src/utils/changeFiles.ts:39` `roundRows(round)` → `ChangeFileList` 要的 `TouchedFile[]` |

## 5. 锚点：卡片挂在哪（本设计唯一的硬决策）

### 5.1 决策：**锚在消息流尾部，跟随当前轮**

- 最新一轮进行中 → 尾部渲染 `正在改` 卡
- 该轮结算 → 同一位置变成本轮结算卡
- 下一轮开始 → 又变回 `正在改`（上一轮的账单退场，面板里留档）

即：它是**跟随当前轮的实时结算条**，不是堆叠的流水账。

### 5.2 依据

1. **核心场景覆盖度 100%**。要它出现的时刻就是"你刚读完回答"——而流式输出本来就
   把视口保持在底部，人一定在流尾。
2. **跨重载行为一致**。`rounds` 从磁盘加载（`<sid>-changes.json`），最新一轮仍在流尾，
   卡片不会出现"看到过、重开就没了"。
3. **零结构成本**。不需要在消息与轮次之间建任何关联。

### 5.3 被否的逐轮锚点（如实记录，供将来重开）

"每一轮回答下方各自挂一张"需要一个稳定的 **「消息 ↔ 轮次」键**。现有一切候选都不成立：

| 候选键 | 为什么不成立 |
|---|---|
| 消息 id | `packages/aide-sdk/src/composables/useChatSession/transcriptMapping.ts:13`：**id 每次重新生成**（`crypto.randomUUID`）→ 跨重载必然失效 |
| 消息字节偏移 | 分页游标确实是字节的（`pagination.ts`，`LoadMessagesResult.nextOffsetBytes/endOffsetBytes`），但**单条消息不带偏移**（`itemsToChatMessages` 只映射内容）；轮上只有 `rewindTo`（轮首字节位置）。要落这个键，得先让后端 `load_messages` 每项带偏移——**那是一条后端缝**，不是前端能自己解决的 |
| 轮序号 ↔ 第 N 条用户消息 | 零成本、跨重载稳定（只依赖序数），但这是一条**无人强制的隐式不变式**：只靠 revert 同时截断 jsonl 与删轮（`useConversationChanges.ts:379-401`）来维持。会话被外部工具改动即错位。列为待定项而非方案 |

**净判断**：逐轮锚点的价值（往回翻能看到第 3 轮的账单）**明显低于**它的成本与脆弱性；
而"往回看"这件事，面板本来就是更合适的载体——它有全部轮次、跨轮统一文件树、逐轮撤回。
卡片上的 `变更面板 ↗` 正是这两者的桥。

### 5.4 已知代价（必须写在明处）

**往回翻看不见历史轮的卡**。历史账单由面板承担。
如果落地后这个代价被证明不可接受，5.3 的第三条是成本最低的重开路径（需先用实证确认不变式成立）。

## 6. 改动面：这一笔**不动逻辑**

先说结论：**没有 sidecar 改动、没有 Rust 改动、没有协议改动、没有落盘格式改动、没有 REGISTRY 改动。**
卡片是既有状态的**新消费者**。这是锚点选在流尾换来的——如果做逐轮锚点，就得先让后端
`load_messages` 每项带字节偏移，那才是真逻辑。

### 6.1 明确「不动」的清单

| 层 | 不动 | 理由 |
|---|---|---|
| `packages/aide-sdk` | **完全不动**（含 types / api / useChatSession） | 会话变更能力是桌面专属（§9），往共享层塞桌面 prop 会背上多端同形的维护义务 |
| `agent-sidecar` / `src-tauri` | 完全不动 | 无协议、无命令、无事件 |
| `useChangeAttribution` | 不动 | 卡片只是它下游的第二个消费者 |
| `useConversationChanges` | 不动 | `rounds` / `revertSingleFile` / 既有 live refresh 全部照用 |
| `ChangeLogPanel` / `ChangeRoundItem` | 不动 | 退化为"完整台账"角色，只多一个来自卡片的入口 |
| `blockSegments.ts` / `ChatMessage.vue:149` | 不动 | 见 §7 上表 |
| 落盘格式 `ChangeRoundData` | 不动 | 无新增字段 |

### 6.2 真正会动的三处（都不是逻辑层）

1. **新增一个卡片组件**（`src/components/...`，桌面侧）+ 在 `ChatPanel.vue` 的
   `.chat-messages-body`（`:514`，`v-for="row in rows"` 之后）追加渲染一处。
2. **把 `rounds` 接到对话流**：目前 `App.vue:322` 的唯一实例只把 props 透传给 `ChangeLogPanel`，
   要再透一份给 `ChatPanel`。**纯接线，且必须停在 `src/` 侧**（不得进 SDK）。
3. **`变更面板 ↗` 的「确保显示」语义**（§2.3.1）：`useRightPanel.select()` 是 toggle，
   不能直接用。二选一——
   - 把既有特例泛化成 `ensureTabShown(id)`（顺手去掉一个特例，但动到浏览器栏路径，有回归面）；或
   - 卡片内手写三行（`tab = "changes"; collapsed = false`），**不碰任何既有代码**。

**建议取后者**：本笔的定位就是前端接线，不为一个入口去动共享 composable；泛化留作独立一笔。

### 6.3 唯一的**展示态**新状态

"本会话首次出现变更时淡入一次"需要 per-session 的一次性标记——纯展示用途，但确实是新状态。
**建议直接砍掉（YAGNI）**：入口本来就常驻可见，淡入只是锦上添花；砍掉后本笔**新增状态为零**。
（若保留，则落在卡片组件内部的 ref，不进任何 store。）

### 6.4 一处必须实测、可能牵出第二笔的地方

卡片是流尾一个**会变高变矮**的元素（不出现 → 出现 → 数字变长 → 展开清单），它会与
`useChatScroll` 的贴底 / "回到底部"逻辑互相看见。**本笔不改那段逻辑**，但必须先实测
（§10 真机 ⑧）。若实测打架，那是**另一笔**改动，届时单独评估——现在不预支结论。

## 8. 边界与**不做的事**

| 项 | 决定 | 理由 |
|---|---|---|
| 撤回整轮 | **卡上不提供** | 我们的 `revertRound` = 杀进程 + 截断 `.jsonl` + 逐文件还原，**不可逆**。在一张每轮自动出现的卡上放一键不可逆操作 = 事故温床。它留在面板（那里有完整确认弹窗）。展开后的**单文件**撤回保留，与面板行为一致 |
| 0 个文件的轮 | 整卡不渲染 | 纯聊天/纯查询的轮次不该凭空多出一张卡 |
| 量级比例条（长度 ∝ 改动量） | **不做** | 需要会漂移的参照，翻历史时回溯缩放（见 2.4） |
| 会话累计行（卡上再加一行"本会话共 12 个文件"） | **暂不做**（待定） | 数据现成（`mergeChangeFiles(rounds)`），但会明显加宽卡片；YAGNI，落地后视需要再议 |
| 卡上展示 diff | **不做** | 一轮 6 个文件各铺一个 diff = 把卡片变成第二堵墙。点文件行开 diff 窗口 |
| 多端（PWA / 鸿蒙） | **本设计明确是桌面专属**，见 §9 |
| 从卡片发起"提交 / 暂存"等 git 操作 | **不做** | 卡片是只读账单 + 两个出口；git 操作归 Git 面板 |

## 9. 多端口径（明确写死，避免将来含混）

会话变更能力目前**只有桌面端有**：

- 归集器与面板都在桌面侧（`src/composables/`、`src/components/`，不在 `packages/aide-sdk`）；
- `load_session_changes` / `save_session_changes` / `git_revert_file` **都不在远程
  REGISTRY**（`src-tauri/src/remote/rpc.rs` 中无匹配），远程客户端调不到。

因此结算卡**只做桌面**，并且：

1. 不往共享 SDK 的类型里加东西（`UserMessageBlock` 那类双份同形的维护义务，不要背）；
2. 不在共享代码里直接 import 桌面组件；
